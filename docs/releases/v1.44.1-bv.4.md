# Rotki BV v1.44.1-bv.4

This maintenance release targets the TRON review findings in [#30](https://github.com/brylovit78/rotkibv/issues/30), on the upstream v1.44.1 base. It is an independent community fork, not an official rotki release.

- Repeated token identities within or across TronScan holdings pages now reject the snapshot and retain previously cached balances. Equivalent hex/Base58 contracts cannot evade the duplicate check.
- Profiles sharing the global database inherit known TRON spam at startup. Python and Colibri asset metadata include its spam flag. The UI's unmark action and the false-positive API clear it; a balance refresh preserves a user's choice to unignore an existing token.
- Transaction refetch accepts equivalent Base58, `41`-prefixed and `0x`-prefixed TRON addresses when the TRON chain is specified, and checks the canonical address against tracked accounts.
- Impossible TRON address lengths are rejected before Base58 decoding.

Regression tests cover each correction, the existing balance-cache fallback, a second profile sharing the global database, non-spam metadata and untracked-address rejection. No schema version or packaged asset database change is required.

## Supported scope

TRON support includes accounts, wallet TRX/TRC20 balances, transaction history, shared history events, fees and manual event corrections. It requires a user-supplied TronScan API key. TronScan receives the queried public addresses and transaction hashes; this integration does not use wallet private keys.

Staking, frozen/resource positions, TRC10, NFTs and protocol-specific DeFi decoding are not included. Balances are wallet balances, not a complete statement of every TRON position. Duplicate detection rejects known ambiguity; it does not make the provider's paginated API an atomic snapshot. See the [integration design](../designs/tron-integration.md) for history completeness and provider limits.

## Container update

The image tag is `ghcr.io/brylovit78/rotkibv:v1.44.1-bv.4` (`linux/amd64`). Use it only after the tag's release workflow succeeds; the GitHub release records the published digest, source commit, review and rehearsal results. Prefer that immutable digest in deployment.

Before updating, stop the existing container and back up all data, config and logs volumes; record the previous image digest. Then set `ROTKIBV_IMAGE` in `deploy/.env`, run `docker compose pull` and `docker compose up -d --wait` from `deploy/`, and verify login, accounts, balances and history. Preserve the existing session key and proxy configuration. For remote access use authenticated ingress and the appropriate HTTPS/Secure-cookie configuration described in [FORK.md](../../FORK.md#розгортання-на-сервері).

Rollback requires the previous image **and its matching volume backup**. Do not remove production volumes or downgrade in place on migrated data. The isolated upgrade/rollback rehearsal in `tools/fork/docker_rehearse.py` checks the published images on synthetic profiles; it does not certify every production portfolio or live provider response.
